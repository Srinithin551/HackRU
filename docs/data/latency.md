## What this means

- **The database meets the 50 ms budget with room to spare.** The two hot-path reads, `get_window_stats` (Brain, every 3 s) and `get_question_stats` (after every answer), execute in **0.07 ms** and **0.17 ms** on Tiger, as index range scans on `(session_id, time DESC)` (plans in [queries.md](queries.md)).
- **The round trip is the network.** A bare `SELECT 1` costs **53 ms** from the dev laptop, and every single-query function lands within 1 to 3 ms of it. No index or query rewrite can go below the floor, so the round-trip target can't be met from this machine and network.
- **It doesn't hurt the product.** Brain's watcher polls every 3 s; a ~53 ms read is under 2% of that interval, and Gemini's ~2 s decision dwarfs it after each answer.
- **Fixed by restructuring:** `compute_baseline` went from 167 ms to 105 ms by running its independent writes and reads in parallel (4 sequential round trips → 3 on first use, 2 after). `get_session_history` and the replay endpoint use one query for all questions, and the replay's three reads run in parallel.
- **Two multi-round-trip calls remain, both once per session:** `compute_baseline` (~105 ms, after calibration) and `end_session` (~103 ms, includes materializing the session in `vitals_5s`).
- **Decision (Likhil, 2026-10-10):** treat 50 ms as the database budget and accept the network round trip. Re-run `python scripts/viz/bench_queries.py` on the demo laptop at the venue. If the floor there is much higher, check the Tiger service region (closest to Rutgers is us-east-1).
